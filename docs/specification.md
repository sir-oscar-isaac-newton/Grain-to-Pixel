# Grain to Pixel: Technical Specification (MVP)

- Status: Draft v0.3, 2026-10-29 (guided RGB capture added)
- Inputs: [product/idea.md](product/idea.md), [structure.md](structure.md), [ADR 0001](../decisions/0001-monorepo.md), [ADR 0002](../decisions/0002-tech-stack.md), [ADR 0003](../decisions/0003-ls-50-via-nkscan.md)
- Principle: KISS. One user at a time, local only, no servers, no accounts. Add complexity only when a measured problem demands it.

## 1. Scope

**Problem:** one app to scan, convert, edit and organize film negatives, replacing paid tools (Nikon Scan 4, Trichroma Lab) for the author and a few friends.

**Core workflow (MVP):**
1. **Ingest:** scan a whole roll (up to 40 frames) on the author's modified Nikon Coolscan LS-50 (RGB + IR), or import R/G/B exposure triplets photographed with a camera (Nikon D600, NEF). Add tags.
2. **Prepare:** detect the frame area, measure the film base.
3. **Convert:** negative to positive.
4. **Edit:** colour balance, tone, geometry, IR dust removal.
5. **Organize:** tagged, searchable archive; export.

**Success metrics**
- *Activation:* a new user completes ingest, convert and export on their first session (measured locally, see §14).
- *Quality:* results comparable to Nikon Scan 4 / Trichroma Lab, judged by the author's blind side-by-side check. Median ΔE2000 against the reference renders is a regression guard, not a quality target, because it mostly measures a difference of look. Each guard uses the setting the app uses (balance off for camera triplets, roll median for scans), and the number of compared frames must not drop: Frontier on triplets, median <= 10 and 95th percentile <= 25, 15 of 15 frames; Neutral on triplets, <= 18 and <= 46, 15 of 15; Neutral on LS-50 scans, <= 17 and <= 29, 11 of 12; Frontier on LS-50 scans, <= 24 and <= 50, 9 of 12. The reference set is private, so the guards run by hand with `benchmark report` before each release that touches the pipeline, not in CI. Calibration and measurements: [benchmark note](research/benchmark.md).

### 1.2 Non-goals

- Masking, local adjustments, AI generation or AI retouching, healing/cloning.
- Digital-camera RAW editing as a general feature (RAW is accepted only as input for RGB triplets).
- Support for other scanners or other LS-50 modifications (only the author's whole-roll LS-50 is targeted).
- Cloud sync, accounts, multi-user, sharing links, social features.
- Printing, soft-proofing, HDR, plugins/extensions.
- Crash/usage reporting to any server; telemetry.
- Camera focus control (the lens is focused by hand), automatic film advance for camera capture, image registration between the three exposures.
- Scanlight firmware flashing, preset saving, or configuration beyond LED levels (use its own web app for that).
- Mobile and Linux builds. Monetization or licensing.

## 3. Architecture

```
┌──────────────────────── Tauri app (single process pair) ─────────────────────────┐
│  WebView (React UI)                    Rust backend (apps/desktop/src-tauri)       │
│  ┌──────────────┐  invoke / events    ┌───────────────────────────────────────┐   │
│  │ Library view │ ◄─────────────────► │ commands/  (thin, validate, delegate) │   │
│  │ Develop view │  binary preview     │ jobs/      (scan, import, export)     │   │
│  │ Import view  │                     │ state/     (open Library, LRU cache)  │   │
│  └──────────────┘                     └──────┬──────────────────────────────┬─┘   │
│                                              │ calls                         │     │
│                    gtp-app (services, JobManager, pipeline composition)            │
│   gtp-ingest  gtp-capture  gtp-negative  gtp-edit  gtp-catalog        gtp-io        │
│          \         |            |           |        /                 /            │
│                                    gtp-core (types)                                 │
└────────────────────────────────────────────────────────────────────────────────────┘
   │ nkscan (USB)    │ USB serial   │ USB (PTP) or     │ SQLite file + files on disk
   Nikon LS-50       Scanlight V4   │ digiCamControl   │ (library folder)
                                    Nikon D600
```

**Rules** (also in [structure.md](structure.md) §4 and `rules/coding.md`)
- Feature crates depend on `gtp-core`/`gtp-io` only, never on each other. The application layer crate `gtp-app` (ADR 0005) composes them: use-case services, `JobManager` and the render pipeline live there. `src-tauri` is a thin adapter over `gtp-app`.
- The UI never touches pixels. It sends a `Recipe` and receives a rendered preview.
- Commands are thin: validate input, call a `gtp-app` service, map errors. No business logic in `src-tauri`.
- Long work (scan, import, export) runs as **jobs** on a worker thread/rayon pool, reports progress by events, and is cancellable.

**Preview transport:** `develop_render` returns raw RGBA8 bytes through `tauri::ipc::Response` (no JSON/base64). While a slider is dragged the UI asks for a 1600 px long-edge render; on release it requests 2048 px. Requests carry a sequence number, and stale results are dropped.

**Concurrency:** one write connection (`Mutex<Connection>`, WAL mode) plus one read connection. A single render at a time per open frame (latest request wins). Export uses a rayon pool sized to `cores - 1`.

### 4.1 Recipe (versioned JSON, stored in SQLite)

```jsonc
{
  "v": 1,
  "geometry": { "crop": {"x":0,"y":0,"w":1,"h":1}, "angle_deg": 0, "rot90": 0, "flip_h": false, "flip_v": false },
  "base":     { "source": "roll" | "manual", "rgb": [r,g,b] },     // film base in linear scan values
  "invert":   { "black": [r,g,b], "white": [r,g,b] },              // per-channel density range; auto-filled
  "color":    { "red_cyan": 0, "green_magenta": 0, "blue_yellow": 0, "temperature": 0, "tint": 0, "saturation": 1.0, "vibrance": 0 },
  "mono":     { "enabled": false, "mix": [0.2627, 0.6780, 0.0593] },    // black and white; mix defaults to Rec.2020 luma
  "tone":     { "exposure_ev": 0, "contrast": 0, "highlights": 0, "shadows": 0, "whites": 0, "blacks": 0, "dehaze": 0, "curve": { "master": [[0,0],[1,1]], "r": [], "g": [], "b": [] } },
  "dust":     { "enabled": true, "threshold": 0.5, "grow_px": 2 },
  "output":   { "space": "srgb", "sharpen": { "amount": 0, "radius_px": 1.0 } }
}
```

Rules: unknown fields are ignored; a missing field means default; `v` bumps only with a migration function in `gtp-core`. "Auto" is just a function that fills the recipe (never a hidden state).

**Ranges.** `Recipe::clamp()` pulls every value into its range (non-finite values fall back to the default) and is idempotent; `migrate` clamps on load and rejects unknown versions with `UnsupportedFormat`.

| Field | Range (default) |
|---|---|
| `geometry.crop` x, y, w, h | fractions of the frame, 0 to 1; w and h at least 0.01; the box stays inside the frame (0, 0, 1, 1) |
| `geometry.angle_deg` | -45 to 45 (0) |
| `geometry.rot90` | quarter turns, wrapped to 0 to 3 (0) |
| `base.rgb` | 1e-6 to 65535, linear scan values (1, 1, 1) |
| `invert.black` / `white` | densities, 0 to 10; white at least 0.001 above black (0 / 1) |
| `color.red_cyan`, `green_magenta`, `blue_yellow`, `temperature`, `tint` | -100 to 100 (0). Positive `red_cyan` adds red, negative adds cyan; likewise green/magenta and blue/yellow, as in darkroom filtration |
| `color.saturation` | 0 to 2 (1) |
| `color.vibrance` | -100 to 100 (0); saturation that spares colours which are already vivid |
| `mono.mix` | each weight -2 to 2 (Rec.2020 luma 0.2627, 0.6780, 0.0593); `mono.enabled` false. Weights summing to 1 keep the brightness; a heavy red weight acts like a red filter |
| `tone.exposure_ev` | -5 to 5 (0) |
| `tone.contrast`, `highlights`, `shadows`, `whites`, `blacks`, `dehaze` | -100 to 100 (0). Highlights and shadows act on the bright and dark parts of the tonal range; whites and blacks move the white and black points; dehaze removes (positive) or adds (negative) a uniform veil |
| `tone.curve.*` | points in the unit square, sorted and unique by input, at most 16 per curve; empty means no change |
| `dust.threshold` | 0 to 1 (0.5) |
| `dust.grow_px` | 0 to 10 (2) |
| `output.sharpen.amount` / `radius_px` | 0 to 150 percent (0, which changes nothing) / 0.3 to 3 pixels of the exported image (1.0) |

### 4.2 Processing pipeline (order is fixed, see `rules/colour-pipeline.md`)

1. **Load** 16-bit source to linear f32. Triplet: decode each NEF to linear (black level subtracted, no white balance or tone curve), demosaic it, then take R from the red-lit exposure, G from the green, B from the blue. The D600's 6016 x 4016 sensor at about 1:1 on a 36 mm frame gives roughly 4,200 ppi, comparable to the LS-50. Capture order is R, G, B by default and can be reordered in the import dialog. Exposures may use different shutter speeds or ISO per colour (typical when balancing the LED channels); the per-channel film-base division in step 4 removes the gain difference, so the only requirement is that no exposure clips. `merge_triplet` (`gtp-ingest`) decodes the three files side by side, interpolates only the lit channel of each (bilinear, reflecting at the edges) and returns the picture with warnings, never errors, for shots whose exposure time, ISO or aperture differ (information when the colours were balanced with the shutter or ISO, a problem for the aperture) and for a lit channel with more than 0.5 % of its samples at 99 % of full scale. The three must be the same size.
2. **IR dust removal** (scans with an IR plane): threshold the normalized IR plane to a mask, dilate by `grow_px`, fill masked pixels from surrounding unmasked pixels (iterative neighbour-weighted fill). Runs before inversion. The plane is read relative to its own clear level (its 90th percentile): a pixel is dust when it reads below `clear * (1 - threshold)`, so a higher threshold masks fewer pixels and a larger `grow_px` more. The mask grows by a square of side `2 * grow_px + 1`, and the fill closes in from the edge of a spot to its centre. Spots (8-connected runs of masked pixels) larger than 0.05 % of the picture, such as the dark band the film holder makes at the edge of the plane, are not dust and are left alone; hairs and scratches are small enough to be removed. A plane that masks more than a quarter of the picture is not showing dust and is ignored. Previews shrink the plane with the scan; the export uses it at full size. A missing or unusable plane skips the stage.
3. **Crop** to the frame area (auto-detected, user adjustable).
4. **Film-base normalize:** `T = I / base` per channel.
5. **Invert:** density `D = -log10(T)` (`T` floored at 1e-6); per-channel black/white densities map `D` to the positive value `P = max(0, (D - black) / (white - black))`, linear in density, with no upper clamp so highlights keep headroom for the tone stage (the output stage clips). The points are auto-filled from the 0.5th and 99.5th percentiles of `D` over the cropped frame; a value the user sets in the recipe is used as is. The white and black pickers set one end from the density of the median of a clicked or dragged area (`levels_from_sample`); the end being set gives way so white stays at least 0.001 above black, and a black or non-finite area is rejected.
6. **Colour:** the red/cyan, green/magenta and blue/yellow axes, temperature and tint as per-channel gains in stops (each control raises its channel(s) and lowers the others so the gains multiply to 1: an axis of +-100 is +-1 stop on its channel); then black-and-white (when enabled: `Y = mix . rgb` in all channels, and saturation and vibrance are skipped); then saturation around the Rec.2020 luma; then vibrance (the same, weighted by `1 - ` the pixel's own saturation). The neutral picker (`neutral_balance`) takes the median of an area sampled before this stage and returns the three axes that equalize its channels at the same brightness (temperature and tint already set supply their share; the axes take `2/3` of the remaining stops); a sample that would need an axis beyond +-100 is rejected.
7. **Tone:** on the Rec.2020 luma, with the pixel scaled by `Y'/Y` so hue is kept: exposure (`2^EV`), contrast (a power curve pivoting on mid-grey 0.18), highlights and shadows (up to 1 stop, weighted by distance from mid-grey; mid-grey is untouched and the mapping stays monotone), whites and blacks (move the white and black points). Then dehaze, global: positive removes a veil estimated as the 0.5th percentile of each pixel's darkest channel and lifts saturation slightly; negative adds a veil. Then curves (monotone cubic, master then R, G, B). Every constant is named in `gtp-edit` and calibrated against reference renders in Q-03.
8. **Geometry:** crop (fractions of the source, rounded to whole pixels), then straighten by `angle_deg` (positive turns the picture clockwise) around the crop centre, then `rot90` quarter turns clockwise, then flips in the final orientation. The straightened output is the largest rectangle with the crop's aspect ratio that fits inside the rotated crop, so there are no empty corners (a few degrees cost a few percent of the frame; `output_size` reports it). Angle 0 copies pixels exactly; any other angle samples each output pixel once, with Catmull-Rom bicubic, at the position of the composed transform. Turns and flips never cause a second resample.

**Pipeline (`gtp-app`):** `render(input, recipe, target)` runs the stages in this fixed order on a clamped copy of the recipe: IR dust (hook; P-12), crop (`geometry.crop`, an exact pixel copy, so later stages and auto levels see only the frame), normalize, invert, colour, tone, geometry (straighten, turns, flips; one resample at most). The film base is the recipe's `base.rgb` when `base.source` is `manual`, otherwise the roll's measured base, falling back to `base.rgb`. `render` never computes automatic values; `analyze` does (on a 1600 px proxy: base unless the roll has one, frame detection on the normalized scan, auto levels on the cropped frame, a render for the histogram) and returns them as a recipe. `Preview { max_edge }` downscales first with an area filter (no overshoot at the rebate edge); the Develop view keeps a 2048 px proxy and previews at 1600 px. Results are linear Rec.2020; `to_rgba8_srgb` converts to sRGB primaries and the sRGB curve for display, and the histogram (256 bins per channel plus luma) is taken from those display values. Per-pixel stages run in parallel over rows (`rayon`) with results identical to a single thread.
9. **Output transform** to the export space with ICC embedded, preceded at export by **output sharpening** (`output.sharpen`): an unsharp mask on the luminance of the image at its final size. The Rec.2020 luma `Y` is encoded as `E = Y^(1/2.4)` (edges are what the eye sees in an encoded image; in linear light the halo would be strong on the bright side and weak on the dark one), blurred with a Gaussian of standard deviation `radius_px` (edges repeated, kernel reaching 3 standard deviations), and `E2 = max(0, E + amount/100 * (E - blur))`; each pixel is then scaled by `E2^2.4 / Y`, so hue and saturation are kept and no colour fringes appear. An amount of 0 changes nothing at all and a flat image stays flat. It runs once, in the export job, after the full-size render and only when the amount is above 0; `render` never sharpens, so previews and thumbnails are never sharpened. The radius is in pixels of the image it is given and is not scaled: a larger export wants a larger radius for the same look, and a future resize option must sharpen after it. Measured on 22 MP frames (release build, this machine): 0.12 to 0.15 s at amount 100, whatever the radius from 0.3 to 3, against an export of 4.2 to 4.4 s.

**Colour management (MVP):** internal working space is linear Rec.2020-primaries f32. Scanner values are assumed linear in that space (no input profile); white balance compensates. Preview assumes an sRGB display. Export spaces: sRGB (default), Adobe RGB, ProPhoto. OS display profiles are post-MVP.

**Frame detection:** on the base-normalized scan the unexposed rebate is about 1.0 and picture pixels are below it, so a pixel counts as rebate when its luminance is within 0.06 of 1.0 (a brightness-step search fails on shadows and on pictures with hard steps). Per axis, the median luminance profile of the columns and of the rows is searched for a rebate band in the first and last quarter; the frame edge is the inner end of each band, and a side without a band keeps the full extent, so one to four rebate sides work. The result is a crop rectangle (the recipe's `geometry.crop`) with a confidence: the share of the outside area that is rebate times the share of the inside area that is not. Confidence below 0.5 selects the full frame and shows a hint. **Camera captures (medium format):** on a roll that is not 35 mm, or that has a frame size, when the rebate search is not confident, near-black pixels (a profile value of 0.02 or less, contiguous from the image edge) are the carrier and not film, and a window of the roll's frame size is slid over the film area to where it covers the most picture, per axis. Without a frame size the window is 0.97 of the largest one of the format's aspect that fits the film area, in whichever orientation fits the picture better. Its confidence is the share of the window that is picture times 0.5 plus half the share of the rest of the film area that is not. Rebate on all four sides measures a frame, and the roll's frame size averages those measurements (the first sets it); a size set by hand in Develop is never replaced. 35 mm scans without a frame size are detected as before.

**Film base:** auto-sample the brightest unexposed border region of the roll's first frame, or the user clicks a rebate pixel. The result is stored on the Roll and used by all frames; a frame can override it (`base.source = manual`). The automatic search takes a thin strip along each border and keeps the brightest; its confidence is the strip's uniformity times how much brighter it is than the interior. Carrier black (a pixel whose brightest channel is below 2 % of the image's 99th percentile) is not film and is left out, so the opaque margins of a camera capture cannot win a strip. An import measures the base on a frame when the roll has none, or only a guess (an automatic base below 0.5 confidence): the measurement is stored when the roll has none, or when it is confident and replaces the guess. A base picked by hand, or a confident one, is never replaced. The roll shows how its base was set (none, picked by hand, measured with its confidence, or a guess that says to pick it in Develop), in the roll sidebar and the Develop base panel (`DevelopInfo.roll_base_confidence`), and an import result says when the roll's base is a guess (`base_is_guess`) or replaced a guess (`base_replaced`, which regenerates the thumbnails of the frames that follow the roll's base).

**Looks (P-19, [ADR 0008](../decisions/0008-film-log-look.md)):** a look is a named set of values that nalyze writes into the automatic recipe, so the recipe stays complete and editable and its schema does not change. *Neutral* (the default) is the conversion as described above. *Film log* is a flat, wide-latitude start for editing: scene light from the density (middle of the frame's black to white range is middle grey, the range is (white - black) / (0.6 * log10 2) stops), encoded with the Blackmagic Film Generation 5 log curve, written as the master tone curve (16 points in linear light, so that the display encoding shows the code values). The Starting look setting (starting_look) chooses the look of frames imported from now on; develop_analyze takes a look (the setting's when none is given) and Develop's Curves section has a button that sets one frame's master curve to it. The gamma of 0.6 is an estimate, not a measured value. *Frontier* ([ADR 0009](../decisions/0009-frontier-look.md)) is a contrasty, saturated lab-print look in the style of the Fuji Frontier SP-3000, fitted to Trichroma Lab's renders: it writes a master curve (a sigmoid with a gamma, as 16 points) and a saturation, the same for every frame, because the automatic levels already normalize each frame's range; `benchmark fit` finds the four numbers.

## 5. Storage

### 5.1 Library folder (user chosen; created by the app)

```
<Library>/
├─ library.db            SQLite (WAL); the source of truth for metadata and recipes
├─ originals/<roll_id>/<frame_id>/
│    scan.tif  ir.tif            (scanner)   or   r.tif  g.tif  b.tif   (triplet)
├─ thumbs/<frame_id>.jpg         512 px, rebuildable cache of the frame as its saved recipe renders it
└─ exports/                      default export destination (changeable)
```

- Originals are written once, as **lossless-compressed 16-bit TIFF** (Deflate with predictor), then marked read-only. RAW triplet inputs are converted to single-channel 16-bit TIFFs on import so the library has one format.
- Thumbnails are the only persisted cache; the editing proxy (2048 px linear f32) is built on frame open and kept in an in-memory LRU of 4 frames.
- Backup = copy the library folder (documented in the README). No cloud features.
- Size planning: an LS-50 frame at 4000 dpi is about 5670 x 3780 px, roughly 128 MB of 16-bit RGB (+43 MB IR) before compression. Expect ~60-100 MB per frame on disk after compression, so ~2.5-4 GB per 40-frame roll. The first-run screen shows free space and the chosen location.

### 5.3 Migrations and integrity

- Forward-only migrations in `gtp-catalog` (`rusqlite_migration`). Before migrating, copy `library.db` to `library.db.bak-v<N>`.
- `PRAGMA foreign_keys=ON; journal_mode=WAL; synchronous=NORMAL`. Run `PRAGMA integrity_check` on open when the previous session ended uncleanly.
- On import, every original is verified by `sha256` after the copy; a *Verify library* action in settings (`library_verify() -> JobId`, a cancellable job) re-checks every original and lists the missing, changed (SHA-256), wrong-size and unreadable ones with their frame and reason. It only reports: it also counts frames without a thumbnail (a rebuildable cache) and lists non-empty folders under `originals/` that no frame owns, and never changes or deletes anything. It works on a read-only library; the time and problem count of the last run are kept in the library (`last_verify_at`, `last_verify_problems`).
- A library from a newer app version opens read-only with a message: `library_info` reports `read_only: true`, reads use a read-only connection, and every write returns `LibraryTooNew`.

### 5.4 App-level settings

`settings.json` in the OS app-config dir: last library path, window size, feature flags, theme, and the keyboard shortcuts the user changed (`keys`, action name to key: only the changed ones are stored, and an empty map is the defaults; at most 64, action names of letters, digits, `.`, `-` and `_`, keys of 1 to 32 printable characters, and no two actions on one key, compared without case). The export presets (`export_presets`, a list of a name and the export options, replaced as a whole by `settings_set`) and the last export (`last_export`: the options and the preset name, if any). A file without `export_presets` starts with two presets, `Archive (TIFF 16-bit)` (TIFF 16-bit, ProPhoto RGB, quality 92) and `Share (JPEG sRGB)` (JPEG, sRGB, quality 90), both with no folder and the template `{roll}_{index:03}`; an empty list stays empty, so deleting both sticks. Names are trimmed and unique without regard to case, the quality is 1 to 100 and the template is not empty and holds no `/` or `\`; a patch that breaks that is refused with `InvalidInput` and saves nothing. The folder of a preset may be empty; `last_export` is stored as given. Per-library values live in the `meta` table.

pub trait ScannerSource {
    fn list_devices(&self) -> Result<Vec<DeviceInfo>>;
    /// Scans `p.frames` in order (1..=40), calling `on_frame` as each completes so it is stored immediately.
    fn scan(&self, p: &ScanParams, on_frame: &mut dyn FnMut(u32, RawScan) -> Result<()>,
            progress: &dyn Fn(f32), cancel: &CancelToken) -> Result<()>;
}

### 6.1 Guided RGB capture (`gtp-capture`)

The Scanlight's serial interface (documented in its repository at `automation/bsl_control_interface.md`, firmware 1.2) is a binary protocol over USB CDC serial: packets are `0xFE`, header byte, data-length byte, data. The commands we use:

| Header | Command | Data | Use |
|---|---|---|---|
| 0 | `SET_COLOR` | R, G, B, W, IR (0-255) and a save flag | light one colour at a time; **always save flag 0** (saving writes non-volatile memory). IR is ignored on v4 |
| 2 | `GET_FW_VERSION` | none | handshake and device identification (the interface defines no VID/PID, so we probe serial ports); accept hardware IDs 1 and 2 (the first half of the version reply; v4 rev A/B), warn on others |
| 3 | `SHUTTER_PULSE` | length in 10 ms units | not used: it does not fire the D600, and the camera is triggered over USB (ADR 0004, amendment 2) |
| 7 | `SET_FOCUS` | 0/1 | not used; not available on the author's rev A (PCB 26a901a) |

The device streams `LED_TEMP` (millidegrees C) and `VBUS` (mV) every 200 ms. Host commands are not acknowledged, and the firmware has no sequence command, so **the app does the sequencing** and treats the link as open-loop (verified by the camera actually delivering a file).

pub trait LightSource {                    // impl: ScanlightV4 (serial), FakeLight (tests)
    fn connect(&mut self, port: Option<&str>) -> Result<LightInfo>;   // probes with GET_FW_VERSION
    fn set_levels(&mut self, rgb: [u8; 3]) -> Result<()>;              // SET_COLOR, save=0
    fn shutter_pulse(&mut self, tens_of_ms: u8) -> Result<()>;         // unused for triggering: the camera is fired over USB
    fn status(&self) -> LightStatus;                                   // last LED_TEMP / VBUS
}
pub trait CameraSource {                   // impl: GphotoCamera (feature `tether`), WatchedFolder, FakeCamera
    fn is_connected(&self) -> bool;                                    // false once the link is gone
    fn arm(&mut self) -> Result<()>;                                   // ready to receive one exposure
    fn trigger(&mut self) -> Result<()>;                               // gphoto: PTP capture; folder: the tool fires it over USB
    fn wait_for_image(&mut self, timeout: Duration) -> Result<CapturedFile>;  // the file name and NEF bytes
}

**Per-frame sequence** (`capture_triplet`, cancellable, one job per frame):
1. Check the light and camera are connected and that the light reports its temperature (refuse to start if no reading arrives within about 1 s). A temperature above the abort limit refuses the start before anything is lit; above the warn limit the sequence goes on, and it is reported as a warning on the frame.
2. For each channel in order R, G, B: `set_levels` with only that channel at its own level; wait `settle_ms` (default 500, cancellable); check the link and the temperature (abort above `temp_abort_c`; abort too if the link or the readings are lost); `arm`; `trigger`; `wait_for_image` (timeout 15 s); emit `capture://step`.
3. `light_off` (all zeros, never saved).
4. Validate: three NEFs received; a supply below 4750 mV (`VBUS`) or a temperature above the warn limit seen during the sequence is a warning too; EXIF exposure time, ISO and aperture identical (warn if not); no exposure clipped (histogram check on the matching channel; warn if more than 0.1 percent of its photosites are saturated).
5. Store as an `RgbTriplet` frame (originals converted to 16-bit TIFFs per §5.1) and hash-verify. The UI then shows the merged frame and waits for the user to advance the film by hand and press Next (or Space).

**Live view (H-14):** on macOS (the `tether` build) the capture view can show the camera's live view over USB through libgphoto2's `capture_preview`: one JPEG frame per `camera_preview_frame`, about 33 frames per second at 640 x 424 on the D600 (7 KB a frame), enough to frame and roughly focus the film (fine focus uses the zoomed view of H-18, below). Live view never lights the Scanlight: the user lights the film with the view's own light controls. The camera is taken out of live view (on Nikon bodies the `viewfinder` setting goes to 0) before every normal capture (the triplet, the test shot and the calibration) and on `camera_preview_stop`, so a capture straight after live view works; the trait is `CameraPreview { preview_frame, preview_stop, ... }` (`GphotoFinder`, `FakeCameraHandle`), kept apart from `CameraSource` like `CameraSettings`. **Focus aids (H-18):** the same trait also gives the camera's own zoomed live view: the zoom steps the camera offers (on the D600 Whole frame, 25 %, 50 %, 100 % and 200 %), moving the zoomed area to a point of the frame, and the reason live view cannot start, which the error then names in words (for example "Live view cannot start: Sequence error. Switch the camera off and on, then try again."); the zoom is reset to the whole frame before live view is left, so the next live view and every capture start unzoomed. With `GTP_FAKE_HW=1` the fake camera serves generated 640 x 424 JPEG frames (a moving bar and a binary frame counter). Windows has no live view yet: the digiCamControl route waits for R-04.

**Capture profile** (stored in `settings.json`): `levels {r,g,b}` (a separate LED level per colour, since the three LEDs need very different levels for one exposure; the defaults 44, 22 and 2 are bare-light values, measured with no film in the gate, and are not balanced for film: the film-base calibration on the author's roll measured red 246, green 168 and blue 156, so the levels must be calibrated per roll or film stock, with a test shot or the automatic calibration), `settle_ms` (default 500), `camera_backend` (`gphoto` | `folder`), `watch_folder`, `temp_warn_c`, `temp_abort_c` (approved defaults of 45 and 55 °C, decided 2026-11-09, tunable; the Scanlight docs give no thresholds, these are safety nets from the spike measurements). A **test shot** command lights one channel, fires, and returns the histogram so levels can be balanced by hand.

**Saved levels, global and per film stock (H-15):** the sliders hold **working levels** that the test shot and Next frame use; they are kept only by an explicit save, as the global default (`levels` above, plus the camera settings of the test shot in `settings.json`) or for a film stock (`saved_levels.stocks` in `settings.json`, keyed by the stock trimmed and lowercased, keeping the user's spelling, at most 64 stocks). A save is possible only after a test shot at the current levels, and remembers that shot's shutter time, ISO and aperture. A roll's levels are resolved from its `film_stock` (free text), then the global default; a roll with no stock, or a stock with no saved levels, uses the default. Each captured frame records how it was lit in `frame.capture_info` (JSON, migration 0009): `{ v, levels, source, stock, exposure }`, where `source` is `stock` or `default` when the levels used equal the saved ones for the roll and `manual` otherwise, and `exposure` holds the camera settings of the red-, green- and blue-lit pictures; frames that were imported or scanned have none. When the levels came from a saved set that carries camera settings and any of the three pictures differs in shutter time, ISO or aperture (a setting missing on either side is no difference), the capture warns `exposure_differs_from_levels`; the UI also says so beside the save buttons when the test shot's settings differ from the saved ones. Levels set by hand compare with nothing. Automatic calibration of the levels is below (H-17).

**Focus check and flatness map (H-19):** the most exact focus check is a real picture. `capture_focus_check(channel, levels)` takes one shot with that colour lit at its level (the same safety as a test shot: refused while a capture runs, light off on every way out, nothing stored) and shows a 1:1 crop of the middle of the lit channel at full sensor resolution (512 x 512 pixels, stretched to its 99.5th percentile) with its sharpness number. Sharpness is measured on 2 x 2 averages of the linear plane, starting on even pixels (that halves the sensor's own noise from one photosite to the next, which does not change with focus, and keeps the film's grain, which spans a few pixels at 1:1): the variance of their 4-neighbour Laplacian divided by the square of the region's mean (a region with a mean near zero counts as 0), so brightness differences between regions matter less, times 10,000 so that a real picture reads about 1 to 30. The same plane gives a 3 x 3 map of sharpness over the frame, each region relative to the best one, and a hint: **flat** (every region at least 0.85), **bowed** (the middle is the best or within 0.05 of it, the eight outer regions are lower by at least 0.15 on average and differ from each other by at most 0.2), **tilted** (one side's three regions, or one corner, is lower than the opposite one by at least 0.2; a corner is named only when it beats the best side by 0.2 more; the softer side is reported) or **unclear**. A map taken on a flat target can be saved as the **flat reference** in `settings.json` (the lens's own field curvature); later maps are divided by it region by region and renormalised, so what is left is the film, and the reference can be cleared. The map is fair only on a frame with even texture (grain in an evenly exposed area, or a flat target such as a printed fine pattern or a graticule slide), since the sharpness of a region depends on its content, and a wide aperture (f/4 to f/5.6) shows the differences best, so the hint says no more than the pattern. With `GTP_FAKE_HW=1` the fake picture has a fine grain that is a little softer towards the edges, a mild bowl.

**Automatic calibration (H-17):** `capture_calibrate(roll, levels, region?)` is a job that starts from the working levels and test-shoots one colour at a time (red, green, blue), each shot with only that colour lit and the light off afterwards, until the brightest pixels of that colour sit just below clipping. It measures the 99.9th percentile of the colour's linear value over the whole frame, or over an optional normalised rectangle (H-20: the user drags it on the whole-frame live view; it is kept while the capture view is open, not saved, and the result says whether the area or the whole frame was measured), aims at 0.93 of full scale (accepted from 0.90 to 0.97, clipped from 0.99) and takes at most 6 shots per colour: a proportional step, since the light is linear in its level, and a halving when the shot is clipped. It fails in words when a colour is clipped even at level 1 (the exposure is too long), too dark even at level 255 (too short), or has not settled in 6 shots, and warns when a final level is below 20, where one step is too coarse. The result (`levels`, `reached`, `shots`, `warnings`) is shown for review and nothing is saved until the user saves it with the buttons of H-15; a finished calibration counts as the test shot that save needs. Bare light leaking past the film's edge is brighter than the base and would pull the levels down, so the film base must fill the frame or the chosen area.

**Validation:** `capture_profile_set` checks the result as a whole and saves nothing when it fails: levels 0 to 255, `temp_warn_c` and `temp_abort_c` finite with warn below abort, `settle_ms` at most 10,000, a watch folder that is a plain path (an empty one clears it). A profile in `settings.json` that fails the same check is replaced by the defaults at load (logged), the rest of the file is kept.

**Shared light, watchdog and busy flag:** the one light is a `SharedLight` (`gtp-app`) that implements `LightSource` and **locks per call**, never for a job, so nothing waits on the lock while a capture settles or blocks in `wait_for_image`. The thread that emits `light://status` every 200 ms is the **watchdog**: above `temp_abort_c` (or lit with no reading) it sets the **tripped** flag and switches the light off (again on each tick while it stays that hot), and `tripped` in the event tells the UI. While tripped, every non-zero `set_levels` is refused ("the light was switched off because it got too hot"), so a running sequence cannot light its next colour and ends with that error; a picture that arrives after a trip also fails the job, which stores nothing. Only `light_connect` clears the flag (reconnect once the light has cooled); a lit light that reports no temperature at all trips too (an unlit one with no reading never does). The driver counts a reading older than 1 s as gone (the light sends one every 200 ms), so a device that falls silent with its port open is caught here and by the sequence's "readings lost" abort. `light_off` always attempts the write, also when the driver says the link is down. `light_set` with non-zero levels first needs a connected light with a current reading under `temp_abort_c` (after the same brief wait for a first reading as a test shot); all zeros are always allowed. A separate **busy flag** is held for the whole of a capture job, a test shot, a `light_connect` and a `light_set`: while it is held those and a second `capture_triplet` are refused with "A capture is in progress", and a guard releases it on every exit, a panic included. `light_off`, the watchdog and the exit hooks ignore it.

**Safety rules:** the app never writes presets or trim (SET_COLOR save flag always 0, no SET_TRIM), turns the light off on cancel, error, panic, window close and exit, and aborts a sequence if `LED_TEMP` exceeds `temp_abort_c`, if the light stops reporting a temperature, or if the link is lost. Window close switches it off (it can be used again if the window is opened again); exit switches it off and refuses every colour from then on. The panic hook makes a best-effort switch-off with `try_lock`, so it can neither deadlock nor panic; if the light's lock is held at that moment it gives up and logs it. A killed process or a power loss cannot be covered: the capture view's own switch-off when it unmounts (U-10) and the physical power switch are the last resort (§17).

**Camera backends**
- `GphotoCamera` (macOS arm64 builds, Cargo feature `tether`): libgphoto2 over USB/PTP; the app sets the colour, triggers capture, and downloads the NEF directly, so no shutter cable is needed. The camera's own controls are locked while it is tethered, so the app reads and sets ISO, shutter speed and aperture itself (libgphoto2 keys `iso`, `shutterspeed` and `f-number`, as menus), through the same worker; focus stays with the lens, which is focused by hand. A dedicated worker thread owns the camera and its session, because libgphoto2's capture call blocks and cannot be interrupted: `trigger` sends the capture request and returns, and `wait_for_image(timeout)` waits for its reply; a request still unanswered at the timeout marks the camera unusable (later calls fail in words until the camera list is refreshed or the app restarts), its late result is discarded, and dropping the camera never waits for the thread. The camera is found when it is first needed, so one plugged in after the app started works. When macOS's own camera helper holds the USB device (`Could not claim the USB device`, for example with Photos open in a second logged-in account) the app says in words to log other accounts out and quit Photos and Image Capture; it never kills processes. libgphoto2 and its camera/port driver libraries ship inside the app bundle (`Contents/Frameworks/gphoto`), and the app sets `CAMLIBS` and `IOLIBS` to them at start.
- `WatchedFolder` (Windows via digiCamControl; macOS fallback): digiCamControl, connected to the camera over USB, fires the D600 and saves each NEF to `watch_folder` (the Scanlight's shutter output is not used); the app waits for new files (`notify`, file-size-stable check). digiCamControl is the only thing that fires the camera. Any other tool that writes NEFs to a folder works the same way.

When the options shown differ from the chosen preset (the folder is ignored for a preset without one, and the JPEG quality for TIFF) the select shows `<name> (modified)` and `Update` is enabled. `Save as preset…` asks for a name inline (not empty, and not one in use, compared without case), `Update` overwrites the chosen preset with the options shown, folder included, and `Delete` asks for a confirmation first; each writes the whole list through `settings_set` and shows a message when that fails. Presets are app settings, so they stay editable in a read-only library. The options of the last export started, and the preset they came from, are kept in `settings.json` (`last_export`), and the dialog starts from them (with the preset if it still exists), or from TIFF 16-bit, sRGB, quality 92 and no folder when there are none. Starting calls `export_start`; the dialog then shows the job's progress bar, Cancel, and at the end a summary (`N files written to <folder>`) with the frames that failed and why; `Export more` returns to the form. Closing the dialog does not stop the job: the Library's Jobs panel lists it, and reopening the dialog shows the running export. A cancelled job says that files already written stay (the job reports no count).
- **Import:** pick source (Scanner / Files), choose roll, enter tags, progress list. Today the view has the **Files** section for camera files (RGB triplets): choose a roll and NEF files, and `triplet_group` shows them as triplets, each file in its channel (red, green, blue) with its capture time. A group with a problem (a missing or extra shot, no capture time, two files of one colour) shows why and cannot be imported. The user reorders the channels of a triplet with "Earlier" and "Later" buttons on each file, confirms the triplets to import (all whole ones start confirmed), and starts `import_files(..., rgb_triplet)` with the confirmed ones flattened in channel order. Progress and Cancel use the job list; when it ends the job shows the frames imported, the skipped files and the warnings of the merge, each naming its frame. Tags are added in the Library; the scanner section comes with U-08. TIFF scan import is started from the Library's roll sidebar (its import button for the selected roll); the Import view's Files section is for camera triplets.
- **Scan a roll** (the Scanner section of the Import view, above Files): shows the scanner found by `scanner_list`, or why there is none (not connected, wrong driver, nkscan missing) with a hint about the WinUSB driver on Windows. For a roll chosen as in Files it takes the first and last frame (1 to 40, with a message for anything else), the resolution (1000, 2000 or 4000 dpi), the samples per pixel and whether to scan the infrared. It offers to continue at the frame after the last one scanned into the roll (`scan_resume_point`) or to start from frame 1, starts `scan_start` as a job, and shows progress and Cancel in the jobs list; a stopped or failed scan keeps the frames before it. "Preview the roll" shows the scanner's thumbnail of the whole roll as a positive strip with lines where evenly spaced frames start (`scan_preview`), and can be stopped. Moving the frame grid and choosing frames is the contact sheet (H-13).
- **Capture** (part of the Import view): connection status for the Scanlight and camera, LED level sliders per colour, test shot with histogram, a Calibrate button (with the hint to frame clear film base) that finds the levels automatically (H-17): it shows the shot it is on, a Cancel button, then per colour the level, how full the range got and the shots it took, and sets the sliders, which counts as the test shot for the save buttons, camera settings (ISO, shutter speed and aperture, read from the camera with the choices it allows, changed here and off while a capture or a test shot runs; the aperture reads "Set on the lens" when the lens has no electronic contacts; one line says what exposure the roll's saved levels were taken at), a Live view panel (H-14: Start and Stop, the camera's picture at about 640 by 424 px with its frame rate, shown a frame at a time; it never lights the Scanlight by itself, but a Light control (Off, Red, Green, Blue, All, at the working levels, re-sent when a slider moves) lights it for framing and focusing and goes back to Off, with the light switched off, on Off, Stop or a frame error; focus aids (H-18: focus peaking, off by default, outlining the sharp edges of each frame in a chosen colour at a chosen sensitivity; a sharpness number, the variance of the Laplacian of the brightness of the middle third of the frame or of the whole zoomed view, with the best value since live view or the zoom started and a Reset best button; and the camera's own zoom steps with a spot to aim at, chosen by a click on the whole frame and moved with arrow buttons) work on the frames in the app, and the zoom goes back to the whole frame when live view is left; it stops when a test shot, calibration or capture starts (the control then just reads Off, as the sequence owns the light) or the view closes, and is offered only with the macOS camera backend), a Focus check (H-19: one picture in a chosen colour at the working levels, shown as a 1:1 crop of the middle with its sharpness number and the best so far, and a 3 x 3 sharpness map with a hint (flat, bowed, tilted towards a side, unclear); the map can be saved as a flat reference and later maps are shown against it; it is fair only on even texture, and a wide aperture shows the differences best), a calibration area (H-20: a drag on the whole-frame live view draws it, a click still aims the zoom, Clear area removes it) that Calibrate measures instead of the whole frame, a large "Next frame" button (Space), the merged result of the last frame, and a running frame counter for the roll. The light is switched off whenever the view closes.

Neutral dark grey surround for colour judgement; no coloured chrome around the image.

## 8. Testing strategy

| Level | Tooling | What |
|---|---|---|
| Unit (Rust) | `cargo test` | each pipeline stage on small synthetic buffers; recipe (de)serialization and migrations; catalog queries on in-memory SQLite |
| Golden images | custom ΔE2000 comparator in `tools/benchmark`, fixtures in `samples/public` | full pipeline output vs stored expected TIFF within tolerance; regenerated only by an explicit command + review |
| Property tests | `proptest` (few) | invert/normalize monotonicity, crop never out of bounds, triplet merge channel mapping |
| Ingest | `FixtureSource` | scan job progress, cancel, error paths without hardware |
| Capture | `FakeLight` + `FakeCamera`; byte-exact packet tests built from the Scanlight interface doc | sequence order R, G, B; light-off on cancel/error/timeout; temperature abort; mismatched EXIF warning; clipping warning; the real `ScanlightV4` encoder/decoder against recorded packets |
| UI components | Vitest + Testing Library + `vitest-axe` | panels, tag chips, search bar, a11y violations |
| End-to-end | WebDriver through msedgedriver on WebView2's debugging port (Windows CI, job `e2e-windows`; ADR 0006) | create library, import fixture, convert, tag, search, export |
| macOS | build + launch smoke test in CI; manual checklist per release | WebKit has no WebDriver |
| Hardware | manual checklist in `docs/research/nkscan.md` | LS-50 roll scan (several frames, IR on) on Windows and macOS before each release that touches ingest || Benchmarks | `criterion` in crates; `tools/benchmark` quality report | enforce §11 budgets; report ΔE vs reference renders |

**CI gates (every PR):** `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test --workspace`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `cargo deny check`, ipc-types up to date (regenerate and diff).
**Sample data:** the project has few colour-negative samples (known risk). The author's reference pairs (raw scan or NEF triplet + Nikon Scan 4 / Trichroma Lab render) live in `samples/private/reference/` (or `samples/public/reference/` if shareable) with a manifest row each; `tools/benchmark` reads them: `benchmark manifest` writes the JSON manifest (format in `tools/benchmark/manifest.example.json`) from a folder of triplets, or of LS-50 scans matched by name to Nikon Scan's positives, and a folder of renders, and `benchmark report` prints the CIEDE2000 difference per frame and overall; the results are in `docs/research/benchmark.md`. Every sample gets a `samples/public/MANIFEST.md` row; generate synthetic negatives (known density wedges) for unit tests so correctness does not depend on real film.
**Definition of done:** tests added, budgets still met, docs/ADR updated if behaviour or structure changed, no new clippy/lint warnings.

## 9. Security and privacy

- **Local only.** The app makes no network calls except the update check to GitHub Releases (user can disable). No telemetry, no accounts.
- **Tauri hardening:** strict CSP (`default-src 'self'`), no remote content, capabilities limited to what commands need; filesystem access only to the library folder and paths chosen through the OS dialog; no shell plugin (if the nkscan CLI fallback is ever used it is an allowlisted sidecar with fixed arguments).
- **Untrusted files:** images from other people are parsed with memory-safe Rust crates; enforce max dimensions (20,000 px per side) and max decoded bytes (2 GB) before allocating. Paths received from the UI are canonicalized and must resolve inside the library or a user-selected directory.
- **Updates:** Tauri updater verifies a minisign signature (public key embedded; private key held only as a GitHub Actions secret). `requireSignedVersion` is on, so a manifest cannot pair a new version number with the signed package of an older release (a forced downgrade); the update endpoint must be `https`. The text of the release notes is shown as plain text, never as markup. The `update_check` flag (section 10) switches the only network call off.
- **Supply chain:** lockfiles committed, `cargo-deny` + `cargo audit` + `pnpm audit` in CI, Dependabot weekly, pin `nkscan` exactly.
- **Data safety:** originals read-only and hash-verified; migrations back up first; destructive actions (delete frame/roll) require confirmation and delete files only after the DB transaction commits.
- **Unsigned builds:** documented install steps (Windows SmartScreen "More info, Run anyway"; macOS first launch via right-click Open). macOS builds use ad-hoc signing (`signingIdentity: "-"`), which Apple Silicon requires to run at all.
- **Serial and camera access:** the Scanlight is opened only through the Rust backend (no Tauri serial plugin, no WebSerial) on a port the user selected or the app probed; all bytes read from it are length-checked and unknown packets are dropped. libgphoto2 is bundled as dynamic libraries with their licence texts. Watched folders are user-chosen and files are validated like any import (§9 untrusted files).
- Scanner on Windows: the coolscan-mods firmware flasher needs VueScan's USB drivers, so the driver stack nkscan can use alongside them (VueScan's driver, or WinUSB via Zadig) must be confirmed in the M0 spike and documented in the user guide.

## 10. Feature flags

KISS: two mechanisms, no external service.
- **Compile-time Cargo features:** `tether` (libgphoto2; on for macOS builds, off for Windows, which uses the watched-folder backend).
- **Runtime flags** in `settings.json` (`flags: { name: bool }`), read through `settings_get`, with defaults in code:

| Flag | Default | Purpose |
|---|---|---|
| `dust_removal` | on | disable if IR output misbehaves on real scans |
| `triplet_import` | on | allow disabling until M5 verified |
| `guided_capture` | on | Scanlight control and camera capture; disable if hardware misbehaves |
| `dev_overlay` | off | per-stage timings and memory in the Develop view |
| `update_check` | on | ask GitHub Releases for a newer version at launch (at most once a day); off means no network request at all |

Each flag has an owner issue and is deleted after one release in which it was fully on.

## 11. Performance budgets

Reference machine: 4-core/8 GB laptop on SSD (2020-class). Measured in CI benchmarks where possible and by hand otherwise; a miss blocks release.

| Metric | Budget |
|---|---|
| Cold start to interactive Library view | <= 2 s |
| Idle memory | <= 300 MB |
| Installer size | <= 40 MB |
| Open a frame in Develop (decode 21 MP TIFF, build proxy) | <= 1.5 s |
| Slider change to updated preview (1600 px during drag) | <= 100 ms |
| Auto analysis (frame detect + base + levels) on proxy | <= 500 ms |
| Full-res export of one 21 MP frame (incl. dust removal) | <= 10 s (4-core), <= 6 s (8-core) |
| Peak memory during export | <= 1.5 GB (single f32 working buffer, in-place stages) |
| Import (copy + compress + hash + thumbnail) per frame | <= 8 s, excluding scan time |
| Triplet merge per frame (3 NEF decodes + demosaic + store) | <= 10 s (measured on D600 files, release build: the three exposures decode and merge side by side in 0.36 to 0.46 s; storing the three planes as 16-bit TIFFs, 2.8 to 3.2 s each, is the rest and also runs side by side; [research](research/nef-decode.md)) |
| Guided capture, Next click to stored triplet (excluding exposure time) | <= 15 s |
| Colour switch (command write to LED lit) | <= 50 ms, plus the configured `settle_ms` |
| Library grid scrolling, 5,000 frames | 60 fps, thumbnails lazy-loaded |
| Search over 50,000 frames | <= 100 ms |

The budgets were calibrated in Q-03 and stay as listed. They were measured on a 6-core desktop ([benchmark note](research/benchmark.md)), and every measured budget is met there. Open before release (Q-07): the run on the reference laptop, and the rows with no measurement yet: cold start, idle memory, installer size, the export's encode and write and full-resolution dust removal (only the render is measured), peak memory during export, guided capture, colour switch, library grid scrolling and search over 50,000 frames.

The scan itself is hardware-bound and not budgeted, but the UI must stay responsive and cancellable throughout. Implementation hints: `rayon` over rows, in-place f32 buffers, `fast_image_resize` for proxies, reuse buffers between renders. If CPU cannot meet the preview budget, first reduce the preview size, then consider GPU, and only then add complexity.

## 12. Observability and logging

- **Logs:** `tracing` with a rolling JSON file in the OS log dir (daily, keep 7 days, cap 50 MB) and human-readable stderr in dev. Levels: `error` (user-visible failures), `warn`, `info` (job start/finish, library open, migrations), `debug` (off by default).
- **Spans** around each pipeline stage and job with durations. Fields include `frame_id`, `job_id`, `stage`, `ms`. Never log pixel data; avoid full file paths at `info`.
- **Frontend errors:** React error boundary and `window.onerror` call `log_client_event`; the user sees a recoverable error screen.
- **Panics:** a panic hook writes a crash note to the log dir and shows a "something went wrong, export diagnostics" dialog on next launch.
- **Diagnostics export:** `diagnostics_export` zips logs, app/OS/version info, DB schema version, flags, local counters (§14) and the last job errors. No images. Friends send the zip manually; nothing is uploaded automatically. The user picks the `.zip` path in the OS save dialog. Logs are cut to their last 2 MB each (16 MB in all), and the library folder and the home folder are replaced by `<library>` and `<home>` in everything copied. The job errors are the last 20 of this session, kept in memory (cancellations are not errors); `details` and messages are scrubbed the same way.
- **Dev overlay** (flag `dev_overlay`): live stage timings and memory for tuning against §11.

## 13. Internationalization and accessibility

**i18n:** all user-visible strings use `t('key')` from `packages/ui/src/i18n/en.json`; dates/numbers via `Intl`. Only English ships in the MVP, so adding a language later is a JSON file. No string concatenation for sentences; units are formatted, not hard-coded.

**Accessibility (target: WCAG 2.1 AA for application chrome):**
- Everything operable by keyboard (grid navigation with arrows, `[`/`]` previous/next frame, slider keys, curve points movable with arrow keys); visible focus rings; logical tab order.
- **Colour keys** in the Develop view: `Q` adds red, `A` cyan, `W` green, `S` magenta, `E` blue, `D` yellow. A press moves the matching slider by 10 steps, Shift+press by 1. Tone sliders have no keys yet. All shortcuts are customizable: the key map is a user setting (action name to key), these keys are only the defaults, and a key assigned to two actions is rejected with a message. The actions are the eight of the Develop view (before/after `\`, previous and next frame `[` and `]`, back to the Library `Escape`, fit `0`, actual size `1`, zoom `+` and `-`) and the six colour keys. A key is one printable character other than space (letters are compared without case, so Shift never changes which action a key means), or the default `Escape`; Settings has a Keyboard section where *Change* takes the next key pressed (Escape cancels, a combination with Ctrl, Alt or Command is refused) and *Reset keyboard to defaults* clears the changes. A change is saved at once and applies the next time the Develop view opens. Shortcuts are ignored while typing in a field and while a dialog is open (a held colour key draws rough previews and the sharp one when it is let go), and every action stays reachable without its key.
- Radix primitives for dialogs, menus and sliders (labelled, ARIA-correct); every control has an accessible name; status/progress uses `aria-live`.
- Contrast >= 4.5:1 for text; colour is never the only signal; respects `prefers-reduced-motion`; UI scales with the OS text-size setting.
- `eslint-plugin-jsx-a11y` in lint, `vitest-axe` on key components, manual screen-reader pass (NVDA, VoiceOver) before v0.1.0.
- The image canvas gets a text alternative (frame name, tags) and is not otherwise inspectable by screen reader.

## 14. Analytics

**No telemetry and no network analytics.** To measure the *activation* metric without sending data, the app keeps local counters in the `meta` table: `first_import_at`, `first_convert_at`, `first_export_at`, `frames_imported`, `frames_exported`, `scans_failed`. Users can view them in Settings and include them in the diagnostics zip when they choose to share. `first_import_at`, `first_export_at` and the frame counts are set per frame as the import and export jobs finish it (a cancelled job keeps what it finished); `first_convert_at` is the first saved recipe; `scans_failed` is counted by the scan jobs (H-03). A counter that cannot be written (a read-only library) never fails the work it counts. Activation = `first_export_at` within the first session. If remote analytics are ever wanted, that is a new ADR with explicit opt-in.

## 15. Deployment and releases

- **Targets:** Windows x64 NSIS installer (`.exe`) and macOS arm64 `.dmg` (ad-hoc signed). No native Windows ARM64 build until someone with an ARM device can test it; the x64 installer is the stopgap there.
- **Installers:** built by the `Bundle` workflow (`bundle.yml`) with `tauri build --bundles nsis` on Windows and `--bundles app,dmg --features tether` on macOS, and kept as artifacts. The NSIS installer installs per user (no administrator rights) and must be at most 40 MB (the workflow fails above that); the dmg size is reported only. `pnpm check:bundle` keeps the settings in `tauri.conf.json` from drifting. Install steps for the unsigned builds (SmartScreen, Gatekeeper) are in [install.md](install.md).
- **Versioning:** SemVer, `CHANGELOG.md` kept from conventional commits. One channel (stable); prereleases use `-beta.N` tags and are not offered by the updater unless the user opts in.
- **Pipeline:** push tag `vX.Y.Z` triggers GitHub Actions: lint/test, then `tauri build` on `windows-latest` and `macos-15`, then a **draft** GitHub Release with installers and the signed `latest.json` for the updater. The author reviews and publishes.
- **Updates:** Tauri updater checks `latest.json` (`releases/latest/download/latest.json`, which skips drafts and prereleases) at launch, at most once a day (the time of the last answer is kept in `settings.json`), and shows a notice with the version and the release notes; Install and Later are the user's choice, nothing is installed silently, and a failed launch check says nothing. A tampered package or manifest does not verify and is not installed (tests with a throwaway key pair in `apps/desktop/src-tauri/tests/fixtures/updater`). To be verified with two real releases (human): updater behaviour on unsigned macOS builds (quarantine flag on the downloaded bundle); the answer goes into `docs/install.md`.
- **Releases:** the steps (version, tag, draft, publish) and the dry run on a prerelease tag are in [release.md](release.md). `release.yml` builds with `createUpdaterArtifacts` (`tauri.release.conf.json`), so pull request builds need no signing key.
- **Rollback:** previous releases stay on GitHub; the library is forward-compatible within a major version (§5.3), and migrations back up the DB so a downgrade is a restore.
- **Environments:** dev (`pnpm dev`) and release only. No staging.
- **User docs:** `docs/` contains install notes (SmartScreen/Gatekeeper), library backup, scanner setup (Windows driver), and known limitations.

| Risk | Mitigation |
|---|---|
| nkscan LS-50 support is Linux-tested and partly inferred; its docs describe roll transport as inferred, and the SA-30 roll-adapter path enabled by the firmware mod is unproven there | M0 hardware spike including multi-frame advance; `ScannerSource` trait; fallback to importing TIFFs scanned in Nikon Scan 4 / VueScan |
| Friends on Windows ARM cannot be supported (no test device) | x64 installer under emulation, documented as unsupported; native ARM64 build once a tester appears |
